# Audit Fabric — 2026-07-29

Audit complet du dépôt `Foxugly/Fabric` au commit `8409c2d`, avec un focus
demandé sur **le pilotage de Claude Code depuis le terminal Fabric**.

## 1. Résumé exécutif

L'ingénierie est propre : `ruff` et `mypy --strict` passent sans une seule
exception, 55 tests verts, typage intégral, architecture en couches lisible
(domain / application / providers / transport). C'est un socle au-dessus de la
moyenne.

Le problème est ailleurs : **la fonctionnalité centrale ne fonctionnait pas.**

1. Le provider `claude_code_local` était **injoignable depuis l'API** — un
   décalage de convention de nommage entre le backend et l'agent faisait
   échouer toute commande Claude avec `NotImplementedError`. Aucun test ne
   traversait la frontière backend↔agent, donc la suite était verte.
2. Le terminal de l'interface ne parlait **que PowerShell**. Le seul moyen
   d'atteindre Claude était de taper `claude …` comme commande shell, ce qui
   échoue (pas de TTY, sortie ANSI, timeout 60 s, aucune continuité de session).
3. Le « streaming » n'en était pas un : le runner lisait le processus jusqu'à
   la fin, puis renvoyait tous les deltas d'un coup.
4. Annuler une commande Claude **coupait la connexion de l'agent**.

S'ajoutait un **trou de sécurité majeur** (P0-2) : Fabric n'avait aucune notion
de propriétaire d'agent, alors que le provider PowerShell expose un shell
distant complet — tout compte authentifié avait donc un accès total à toutes les
machines Windows enregistrées. Aggravé par le fait que `create_dev_user` créait
systématiquement des superutilisateurs, ce qui rendait le problème invisible à
l'usage.

Tout cela est corrigé et vérifié en conditions réelles (§4).

## 3. Constats

Sévérité : **P0** bloquant · **P1** sérieux · **P2** à traiter · **P3** confort.

### P0-1 — `claude_code_local` injoignable depuis l'API — CORRIGÉ

Le backend émet des actions **qualifiées** (`claude_code_local.message.send`,
imposé par `ALLOWED_ACTIONS` et `ALLOWED_PROVIDER_ACTIONS`). Le
`CommandDispatcher` les transmettait telles quelles au provider. Or
`ClaudeCodeLocalProvider.execute` ne reconnaissait que `message.send` :

```python
if action != "message.send":
    raise NotImplementedError(f"Unsupported claude_code_local action: {action}")
```

Toute commande Claude venue de l'API échouait donc systématiquement.
`windows_powershell` matchait au contraire les noms qualifiés — deux conventions
opposées dans le même dépôt. Invisible en test : les tests provider utilisaient
les noms courts, le test transport utilisait un dispatcher factice.

**Correction.** Le namespace qualifié devient la convention unique sur le fil
(API, base, protocole, `capabilities`). `CommandDispatcher.local_action()` retire
le préfixe en un point unique ; les providers ne voient plus que leur action
courte ; `windows_powershell` a été aligné. Test de non-régression ajouté.

### P0-2 — Aucune autorisation par agent — CORRIGÉ

`Agent` n'a pas de champ propriétaire. Conséquences, pour **tout** utilisateur
authentifié, quel qu'il soit :

- `GET /api/v1/agents/` liste tous les agents de l'instance (`AgentViewSet.queryset`
  n'est jamais filtré) ;
- `POST /api/v1/agents/<id>/development-token` émet un token d'agent valide pour
  n'importe quel agent — c'est-à-dire l'identifiant permettant de se faire passer
  pour cet agent sur le WebSocket ;
- `POST /api/v1/commands/` accepte n'importe quel `agent_id`
  (`CommandCreateSerializer.validate` vérifie l'existence, pas l'appartenance) ;
- l'action autorisée `windows_powershell.command.run` accepte une chaîne
  arbitraire évaluée via `[scriptblock]::Create()`.

Chaîné : **n'importe quel compte Fabric obtient l'exécution de code arbitraire
sur n'importe quel PC Windows connecté.** `AgentViewSet` est de surcroît un
`ModelViewSet` complet, donc `DELETE /api/v1/agents/<id>/` est ouvert à tous.

Accessoirement, `EventConsumer` inscrit chaque utilisateur au groupe global
`events.agents` : tout le monde voit les changements d'état de tous les agents.

**Correction.**

1. `Agent.owner` (FK nullable) + migration `0002_agent_owner` ; un agent sans
   propriétaire est désormais **staff-only** (cas des lignes héritées) ;
2. `AgentViewSet.get_queryset()` filtre sur le propriétaire, ce qui couvre
   d'un coup `retrieve`, `update`, `destroy`, `development-token` et `revoke` —
   tous répondent 404 à un tiers ; `perform_create` attribue l'agent au créateur ;
3. `resolve_owned_agent()` valide l'appartenance dans `CommandCreateSerializer`
   et `ConversationCreateSerializer` ; « inconnu » et « pas à toi » sont
   volontairement indiscernables ;
4. `events.agents` supprimé : la présence n'est diffusée qu'au propriétaire ;
5. `--owner` sur `create_dev_agent` / `ensure_dev_agent` (obligatoire, échec
   explicite si l'utilisateur n'existe pas) ;
6. `create_dev_user` ne crée **plus** un superutilisateur par défaut — il fallait
   `--staff` explicitement. C'est ce qui rendait le trou invisible en pratique :
   tous les comptes de développement étaient administrateurs.

Vérifié en réel avec un compte non-staff : liste vide, 404 sur l'émission de
token et la suppression, 400 sur la création de commande. Huit tests dédiés
(`tests/test_agent_authorization.py`).

**Limite assumée** : un compte `is_staff` voit et pilote tous les agents. C'est
volontaire (administration), mais cela veut dire qu'un compte staff équivaut à
un accès root sur toutes les machines enregistrées. N'accorder `--staff` qu'à
soi-même.

### P0-3 — Le streaming n'était pas incrémental — CORRIGÉ

`ClaudeCodeCliRunner.stream()` lisait `stdout` jusqu'à EOF, accumulait tous les
deltas dans une liste, puis rendait `(deltas, result)`. Le provider les émettait
ensuite en boucle. Résultat : aucune sortie pendant tout le tour, puis tout d'un
bloc — exactement ce qu'un terminal ne doit pas faire.

Deux bugs latents dans la même fonction :

- `stderr` n'était lu qu'**après** `stdout` : au-delà de 64 Kio sur `stderr`, le
  processus `claude` se bloque et le tour se fige jusqu'au timeout ;
- `StreamReader.readline()` gardait la limite par défaut de 64 Kio, alors qu'une
  ligne `stream-json` contenant un résultat d'outil la dépasse facilement →
  `ValueError` en pleine session.

**Correction.** `stream()` est un vrai générateur asynchrone qui émet chaque
delta à l'arrivée ; `stderr` est drainé en parallèle ; `limit` porté à 8 Mio ;
deadline unique par tour au lieu de trois `wait_for` empilés. Les appels d'outil
sont désormais remontés comme événements `message.tool_use`, ce qui rend
l'activité visible pendant un long tour.

### P0-4 — L'annulation coupait la connexion de l'agent — CORRIGÉ

`ClaudeCodeLocalProvider` n'implémentait pas `cancel()`. La classe de base lève
`NotImplementedError`, qui remontait `_cancel_active_command` →
`_handle_message` → la boucle `async for` du WebSocket → `_run_once` → déconnexion
et reconnexion complète. De plus `task.cancel()` n'arrête pas un processus
enfant : le `claude` restait orphelin.

**Correction.** `cancel()` implémenté : l'exécuteur garde les processus vivants
indexés par `_fabric_command_id` et tue le bon. `_cancel_active_command` absorbe
désormais `NotImplementedError` pour qu'aucun provider ne puisse faire tomber la
socket. Vérifié en réel (§4).

### P1-1 — Le terminal ne pouvait pas atteindre Claude — CORRIGÉ

`app.component.ts` envoyait toute ligne saisie vers
`windows_powershell.command.run`. Taper `claude …` lançait donc la CLI dans la
session PowerShell persistante — ce qui ne peut pas marcher : `stdin` de cette
session est le canal par lequel Fabric injecte ses propres scripts (une CLI
interactive consommerait les commandes suivantes), pas de TTY, sortie capturée
ligne à ligne via `ToString()`, et timeout à 60 s.

Symétriquement, le provider `claude_code_local` n'était atteignable que par
l'API `conversations`, dont aucune UI n'existe.

**Correction.** Le terminal route désormais `claude …` / `claude:…` vers
`claude_code_local`, sans exiger de session PowerShell, avec continuité de
session, choix du mode de permission, streaming et annulation.
Voir [claude-in-the-terminal.md](claude-in-the-terminal.md).

### P1-2 — Aucune option d'exécution Claude — CORRIGÉ

Le runner n'émettait que `-p --output-format …` et éventuellement `--resume`. En
mode non interactif, sans `--permission-mode`, Claude Code ne peut pas demander
d'autorisation : tout outil qui en exige une est refusé, et le tour se termine
par un « je n'ai pas pu ». La fonctionnalité était donc bridée à du texte.

**Correction.** `permission_mode`, `model`, `allowed_tools`, `disallowed_tools`
sont validés côté agent et transmis à la CLI. L'UI envoie `acceptEdits` par
défaut, `claude:mode plan` permet un tour en lecture seule.
Le compromis est documenté explicitement.

### P1-3 — Verrou de session fuité si le flux est abandonné — CORRIGÉ

Le provider tient un `asyncio.Lock` par session **à travers ses `yield`**. Si le
consommateur s'arrête en cours (socket coupée, tâche annulée), le générateur
reste suspendu sur un `yield` et son `finally` ne s'exécute jamais : le verrou
n'est plus jamais rendu, et toute commande suivante sur la même session bloque
indéfiniment.

**Correction.** `contextlib.aclosing` au niveau du dispatcher et du client
transport, pour que la chaîne de générateurs soit finalisée dans tous les cas.
Test de non-régression ajouté.

### P1-4 — Commandes zombies à la déconnexion de l'agent — CORRIGÉ

Rien ne reprenait la main sur les commandes `dispatched` / `running` quand
l'agent disparaissait : elles restaient « en cours » pour toujours, et l'UI
restait verrouillée (`activeCommandId` jamais libéré, bouton *Cancel* inopérant).

**Correction.** `AgentConsumer._mark_offline` bascule les commandes en vol en
`failed` avec un message explicite et publie l'événement. Test ajouté.

### P1-5 — `Command.timeout_seconds` n'était jamais transmis — CORRIGÉ

Le champ existe, est validé (1 à 3600 s), voyage dans l'enveloppe protocole… et
n'était jamais lu par l'agent, qui utilisait uniquement le `timeout_seconds` du
*payload* (défaut 300 s pour Claude, 30 s pour PowerShell). Le réglage côté
serveur était donc décoratif.

**Correction.** Le client transport injecte `_fabric_timeout_seconds` dans le
payload ; l'exécuteur Claude s'en sert comme valeur par défaut. Le comportement
de `windows_powershell` est inchangé (sa borne de 120 s reste la référence).

### P1-6 — Aucune journalisation nulle part — CORRIGÉ (agent)

Aucun `import logging`, aucun `print`, aucun réglage `LOGGING` dans tout le
dépôt. Le pire cas était `AgentWebSocketClient.run_forever` :

```python
except Exception:
    await asyncio.sleep(backoff)
```

Un mauvais token, une URL invalide ou un pare-feu produisaient exactement la
même chose : un agent silencieux qui ne se connecte pas, sans un mot d'explication.
`FABRIC_LOG_LEVEL` figurait dans `.env.example` sans être lu par personne.

**Correction.** `logging.basicConfig` piloté par `FABRIC_LOG_LEVEL`,
journalisation des connexions, des échecs de connexion et des commandes en
échec. Côté backend, `LOGGING` reste à configurer (P2).

### P1-7 — Documentation de sécurité fausse — CORRIGÉ

`docs/windows-powershell-provider.md` affirmait :

> It does **not** expose an arbitrary remote shell.
> - no arbitrary PowerShell script payload
> - no arbitrary shell command payload

C'était faux dès le commit initial : `_run_command` accepte un `command` brut
évalué par `[scriptblock]::Create()`. Un document de sécurité qui décrit
l'inverse du code est plus dangereux qu'une absence de document.

**Correction.** Le document dit maintenant ce que le code fait, et énonce les
règles d'exploitation qui en découlent.

### P1-8 — Pas de CI — CORRIGÉ

Aucun `.github/workflows`. `ruff`, `mypy` et `pytest` étaient configurés et
verts, mais rien ne les exécutait à la place d'un humain — et c'est précisément
ce qui a laissé passer P0-1 (les deux moitiés du système étaient testées
séparément, jamais ensemble).

**Correction.** `.github/workflows/ci.yml` : lint + types + tests des deux
paquets Python, `makemigrations --check` (les migrations ne peuvent plus
diverger des modèles), typecheck et build de production du frontend.

Surtout, la cause racine est traitée : `shared/protocol/actions.py` devient le
**catalogue unique** des actions. Le backend en dérive `ALLOWED_ACTIONS` et
`ALLOWED_PROVIDER_ACTIONS`, les providers déclarent leurs actions et leurs
capabilities en découlent. `tests/test_action_catalogue.py` vérifie que le
registre couvre exactement le catalogue : un décalage comme P0-1 échoue
maintenant en CI au lieu d'échouer chez l'utilisateur.

### P1-9 — Un agent pouvait écrire dans les commandes d'un autre — CORRIGÉ

Découvert en corrigeant P2-6. Le consumer chargeait les commandes par
`Command.objects.get(id=payload["command_id"])`, **sans filtrer sur l'agent
émetteur**. N'importe quel agent authentifié pouvait donc écrire un résultat,
une erreur ou des deltas dans la commande d'un autre agent — donc d'un autre
utilisateur — en devinant un identifiant.

**Correction.** `_load_command()` filtre sur `agent_id=self.agent.id` et
journalise le rejet. Au passage, la machine à états `ALLOWED_TRANSITIONS`
(définie et testée mais jamais appliquée) est maintenant vérifiée à chaque
transition : un message tardif ou rejoué ne peut plus ressusciter une commande
terminée.

### P3 — Confort

- `requires-python = ">=3.12"` sans borne haute : Django 5.2 ne supporte
  officiellement pas Python 3.14 (utilisé ici sans incident, mais non couvert).
- `windows_powershell/session.py` fait 842 lignes dont ~450 de PowerShell
  concaténé en chaînes Python — illisible et non testable unitairement ;
  candidat naturel à des fichiers `.ps1` embarqués.
- `app.component.ts` fait ~1 400 lignes : template, styles, état terminal, état
  Claude et couche transport dans une seule classe. À découper avant la
  prochaine fonctionnalité.
- `NetworkRecoveryPolicy` peut couper la carte réseau de la machine. Désactivé
  par défaut, mais mérite un avertissement explicite dans la doc.
- ~~`ClaudeCodeLocalCapabilities` annonce `session.attach` et `message.cancel`,
  qui ne correspondent à aucune action~~ — corrigé : les capabilities dérivent
  désormais du catalogue partagé, donc elles ne peuvent plus mentir.

## 6. Ce qui reste ouvert

Rien de bloquant. Par ordre de valeur :

1. **Pont d'autorisation des outils Claude.** Aujourd'hui le terminal envoie
   `acceptEdits` : Claude modifie des fichiers sans confirmation. Claude Code
   accepte `--permission-prompt-tool` (via un serveur MCP local) : brancher
   dessus ferait remonter chaque demande d'autorisation dans la page web, avec
   un bouton Autoriser / Refuser. C'est le vrai déblocage produit — on pourrait
   alors travailler en mode par défaut plutôt qu'en `acceptEdits`, et
   `CommandStatus.WAITING_USER_ACTION` (déjà modélisé) prendrait enfin son sens.
2. **Session Claude persistante.** Un tour = un processus `claude -p`. Avec
   `--input-format stream-json`, l'agent peut tenir un processus ouvert et
   pousser les tours dedans : latence et coût de mise en cache réduits.
3. **Interface dédiée à Claude** à côté du terminal (voir §7).
4. **Tests frontend** : aucun runner n'est configuré ; le typecheck et le build
   sont le seul filet.
5. **Découpage de `app.component.ts`** (~1 400 lignes) et de
   `windows_powershell/session.py` (~840 lignes, dont ~450 de PowerShell en
   chaînes Python).
6. **Expiration des tokens** DRF, aujourd'hui éternels et stockés en
   `localStorage`.

## 7. Sur la console comme interface

La console est le bon choix pour PowerShell : c'est littéralement l'interface
native, et le streaming ligne à ligne y est fidèle.

Pour Claude, elle atteint vite ses limites : les prompts sont multi-lignes, les
réponses contiennent du Markdown et du code, les appels d'outils gagnent à être
repliables, et une demande d'autorisation n'a pas de représentation naturelle
dans un flux de texte. Une **vue scindée** — terminal PowerShell d'un côté, panneau
de conversation de l'autre, partageant le même répertoire de travail et le même
agent — garderait la force de chaque surface. Le backend est déjà prêt pour
cela : `apps/conversations` porte la continuité de session, il ne manque que
l'interface.

À garder tel quel en revanche : le routage par préfixe (`claude …` dans la même
zone de saisie). Ne pas avoir à choisir un mode avant de taper est précisément
ce qui rend l'outil fluide.
